# Architecture

The NR Repository Composer is a Yeoman-based generator suite for scaffolding
NRIDS applications. It creates GitHub Actions workflows, Backstage catalog files,
database migrations, and deployment configurations for repositories.

## Core components

- **Generators** — each subdirectory of `src/` is a Yeoman generator. The
   compiled output lives in `generators/`.
- **Utilities** — shared code in `src/util/`:
     - `prompts.ts` — prompt definitions and validation
     - `yaml.ts` — Backstage `catalog-info.yaml` manipulation and path mappings
     - `backstage.storage.ts` — reading/writing Backstage files
     - `git.ts` — Git repository operations
     - `github.ts` — GitHub API interactions
     - `base-generator.ts` — shared generator boilerplate
     - `options.ts` — command-line option definitions
     - `constants.ts` — shared constants
     - `nrsay.ts` — terminal banner output
     - `report.ts` — end-of-run reporting
- **Templates** — each generator has a `templates/` folder with EJS templates.
- **Container** — the `Dockerfile` packages the tool for distribution.

## Key files

- `src/backstage/index.ts` — Creates Backstage catalog files
- `src/gh-maven-build/index.ts` — Java/Maven pipeline generation
- `src/gh-nodejs-build/index.ts` — Node.js pipeline generation
- `src/gh-common-mono-build/index.ts` — Monorepo build orchestration
- `src/util/yaml.ts` — Central configuration for YAML path mappings

## Source layout

| Path | Purpose |
| --- | --- |
| `src/` | TypeScript source for all generators and utilities |
| `src/*/templates/` | EJS/YAML templates (committed, not compiled) |
| `src/util/*-templates/` | Shared templates for helper functions (committed) |
| `generators/**/*.js` | Compiled output — gitignored, regenerated by `npm run build` |

## The base generator

All generators extend `BaseGenerator` (in `src/util/base-generator.ts`), which
handles the common boilerplate:

- Constructor options (`--headless`, `--help-prompts`)
- Storage initialization (a `BackstageStorage` instance)
- The prompting lifecycle (banner, help prompts, bail-on-unanswered)
- Backstage documentation tracking
- End-of-run reporting

Subclasses set instance properties in their constructor:

- `this._nrsayConfig` — `{ title, subtitle, links }`, or `null` to skip the banner
- `this._questions` — array of prompt definitions (default: `[]`)
- `this._storageOptions` — `{ kind, storageOptions }` for `BackstageStorage`
- `writing*()` methods — actual file generation logic
- `end()` — only if custom cleanup beyond reporting is needed

A minimal generator looks like this:

```ts
import { BaseGenerator } from '../util/base-generator.js';
import { PROMPT_PROJECT, PROMPT_SERVICE } from '../util/prompts.js';

const questions = [PROMPT_PROJECT, PROMPT_SERVICE];

export default class extends BaseGenerator {
  constructor(args, opts) {
    super(args, opts);
    this._nrsayConfig = {
      title: 'My Generator',
      subtitle: 'Does a thing',
      links: [['Documentation', 'https://example.com']],
     };
    this._questions = questions;
   }

  writing() {
    this.fs.copyTpl(
      this.templatePath('template.yaml'),
      this.destinationPath('output.yaml'),
      { variable: this.answers.variable },
     );
   }
}
```

## Workflow input parameters

### preflight.yaml

- `preflight_context`: `'build'` or `'deploy'`
- `catalog_info`: Path to catalog file

### check-build-artifact.yaml

- `service`: Service name (empty for top-level workflow detection)
     - Empty: checks the top-level `build-release.yaml` workflow
     - Provided: checks the monorepo job for that service

### Monorepo vs single service

**Top-level workflows** are used when a repository has one service:

- The `service` parameter is empty or not provided
- The workflow runs at the repository root

**Monorepo workflows** are used when a repository has multiple services:

- The `service` parameter contains a service name
- The workflow runs as a job within `build-release.yaml`
- The script detects the git root and sets the container working directory

## Code style

- Use ES6 modules (`import`/`export`)
- Async/await for promises
- Destructure imports: `import { CONST } from './file.js'`
- Add JSDoc comments for utility functions
- Keep generators focused on a single responsibility
- Use `chalk` for colored terminal output
- Validate user input early

## Debugging

- Set `PULL_IMAGE="false"` for faster iteration
- Use `--help-prompts` to see prompt documentation
- Use `--ask-answered` to re-prompt all questions
- Check generator output in `.yo-rc.json` and `catalog-info.yaml`
- Container logs are available via `podman logs` or `docker logs`
- Test generators locally with `npm link`
